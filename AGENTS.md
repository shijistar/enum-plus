# AGENTS.md

Guidance for AI coding agents working in this repository. The human contribution
workflow (development setup, PR process, commit conventions) lives in
[CONTRIBUTING.md](./CONTRIBUTING.md); this file documents the architecture and
the commands needed to change code correctly.

## Project overview

`enum-plus` is a zero-dependency, TypeScript-first "enhanced enum" / business
dictionary library: a drop-in replacement for native `enum` that adds stable
keys, labels, localization, plugins and helper collections. It is published to
npm as `enum-plus` and is designed to work in browsers, Node.js, React Native,
Taro, mini-programs, and SSR.

Constraints that shape almost every change:

- **No runtime dependencies.** Never add entries to `dependencies`.
- **Bundle size is a feature.** Min+gzip is roughly 2 KB — run `npm run size:es`
  when touching shipped code, and avoid unnecessary top-level exports.
- **The public API is [src/index.ts](./src/index.ts).** Anything not re-exported
  there is internal.
- **Backward compatibility is a hard requirement.** `engines.node` is
  `>=7.10.1` and the package ships CJS, modern ESM, legacy (ES2015/IE11) ESM and
  UMD builds. Shipped source in `src/` must compile down to all of these
  targets: do not use APIs or syntax unavailable on Node 7 or IE11.

## Source architecture (`src/`)

| File                    | Responsibility                                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `index.ts`              | Public entry: all exported types plus `Enum`, `PluginFunc`, the symbols/guards and `version`                                                     |
| `enum.ts`               | The `Enum(...)` factory, `IEnum` / `EnumInterface` / `EnumInitOptions`, init normalization, `PluginFunc`                                         |
| `enum-items.ts`         | The items collection: lookup, `toList` / `toMap`, `IEnumItems`, `ToListConfig`                                                                   |
| `enum-item.ts`          | A single item: `key`, `value`, `label` and its localization, `EnumItemInterface` / `EnumItemOptions`                                             |
| `enum-collection.ts`    | Key / value / label lookup helpers over a collection                                                                                             |
| `auto-localize.ts`      | Label template resolution and switchable localization (`LocalizeTemplate*`)                                                                      |
| `localize-interface.ts` | The `LocalizeInterface` contract implemented by localization plugins                                                                             |
| `utils.ts`              | Symbol constants (`KEYS`, `ITEMS`, `VALUES`, `LABELS`, `NAMED`, `META`), `IS_ENUM` / `IS_ENUM_ITEM(S)` guards, `ENUM_OPTIONS`, `defaultLocalize` |
| `global-config.ts`      | Global configuration — explicitly marked **"Internal module, do not use."**                                                                      |
| `types.ts`              | Shared conditional/mapped types for key, value and label inference                                                                               |
| `extension.d.ts`        | Global type extensions (excluded from coverage builds)                                                                                           |
| `version.ts`            | **Generated** by `npm run gv` from `package.json.version`                                                                                        |

## Build & packaging

`npm run build` cleans, then runs the `build:*` scripts in parallel. Outputs:

| Output                 | Content                                                        | Target                      |
| ---------------------- | -------------------------------------------------------------- | --------------------------- |
| `lib/`                 | CJS (`ts2lib` → `tslib/`, then `copy-lib.ts`)                  | `main` (require)            |
| `es/`                  | Modern ESM via `father build`                                  | modern browsers / `import`  |
| `es-legacy/`           | ESM built with `LEGACY=1`                                      | ES2015 / IE11               |
| `umd/`                 | `enum-plus.min.js` and `enum-plus-legacy.min.js`               | `<script>`                  |
| `tses/`                | TypeScript compiled via `tsconfig.es.json`                     | test-only ESM runs          |
| `types-legacy/pre-v5/` | Patched `.d.ts` for TypeScript < 5 (`scripts/legacy-types.ts`) | consumers on old TypeScript |

Post-build steps rewrite the emitted files — do not undo them:
`task:add-es-extensions` (appends `.js` to relative ESM import specifiers),
`task:update-es-enum` / `task:update-es-legacy-enum` / `task:update-lib-enum`
(strip `/// <reference>` and prepend `import './extension'`),
`task:add-umd-banner`, and `task:legacy-types`.

The `exports` map in [package.json](./package.json) selects the right artifact
per condition (`import`, `require`, `types`, legacy). Keep it in sync with the
outputs above when the build changes.

## Testing

Tests are written once and executed under every framework and bundle
combination:

- `test/test-suites/*.ts` — framework-agnostic suites (`create-enum`,
  `enum-item`, `enum-items`, `enum-collection`, `extension`, `interface`,
  `localization`, `plugin`, `version`). This is where new behavior tests belong.
- `test/engines/` — the abstraction layer: `TestEngineBase` plus
  `createEngine('jest' | 'playwright' | 'vitest-node' | 'vitest-browser')`, with
  each test split into `evaluate` (runs in the target environment) and `assert`
  (verifies the result). `test/engines/types.ts` defines the contract.
- `test/specs/{jest,vitest,playwright}/` — thin per-framework adapters that
  consume the shared suites. These are the only framework-specific files.

Rules when adding tests (see [docs/testing.md](./docs/testing.md)):

- The `evaluate` and `assert` bodies **must stay serializable** — no closures and
  no captured outer state. Return from `evaluate` anything `assert` needs.
- The same behavioral test must pass on Node CJS/ESM, browsers and the
  `es-legacy` build; avoid environment-specific assumptions.
- **100% coverage is enforced** for statements, branches, functions and lines —
  in [vitest.config.ts](./vitest.config.ts) and all four Jest configs
  ([jest.config.js](./jest.config.js), [jest-cjs.config.js](./jest-cjs.config.js),
  [jest-esm.config.js](./jest-esm.config.js),
  [jest-legacy.config.js](./jest-legacy.config.js)). Uncovered new code fails
  the suite.
- Prefer extending an existing suite in `test/test-suites/` over adding a new
  framework-specific spec.

## Code style & conventions

- Linting and formatting are owned by `@tiny-codes/code-style-all-in-one`:
  ESLint flat config in [eslint.config.mjs](./eslint.config.mjs)
  (`react-easy-recommended` + Storybook rules), and Prettier, Stylelint and
  Commitlint re-exported by [prettier.config.mjs](./prettier.config.mjs),
  [stylelint.config.mjs](./stylelint.config.mjs) and
  [commitlint.config.mjs](./commitlint.config.mjs). Do not hand-edit style rules
  or add ad-hoc overrides; fix the code.
- Husky + `lint-staged` run on commit: pre-commit applies `eslint --fix`,
  `stylelint --fix`, `prettier --write`; commit-msg enforces
  **Conventional Commits** via Commitlint (`feat: ...`, `fix(scope): ...`).
- 2-space indentation; `camelCase` for variables and functions, `PascalCase` for
  classes and components.
- Public API documentation comments are **bilingual**: `- **EN:** ...` followed
  by `- **CN:** ...` on every public symbol.
- User-facing docs are maintained as EN + `zh-CN` pairs (`README.md` /
  `README.zh-CN.md`, `docs/*.md` / `*.zh-CN.md`). Update both when behavior
  changes.
- Keep pull requests focused on a single topic, with tests and docs updated
  alongside the code.

## CI & release

- `.github/workflows/test-on-commit.yml` runs on pushes to `main`, `next` and
  `v*`, and on PRs to `main`, delegating to `reusable-test.yml` with
  `use-matrix: true`.
- Node matrices in CI: CJS modern **14.x–26.x**, CJS legacy **7.x–13.x**, ESM and
  es-legacy ESM **16.x–26.x**, plus a source unit-test job (`npm test`), browser
  tests. Never introduce a Node API newer than v7 into shipped code.
- The legacy jobs reinstall pinned old dependencies from
  [package-legacy-node.json](./package-legacy-node.json) — keep that file in
  sync when dependencies change.
- `.github/workflows/npm-publish.yml` publishes on release; `prepublishOnly`
  runs `build` + `test-all`, so the full matrix must be green before publishing.
- `.github/workflows/storybook-pages.yml` deploys the docs site;
  `first-pr-welcome.yml` and `stale-issues.yml` are bot housekeeping.

## Graft — repo context graph

This repo is indexed in `graft/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `graft map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `graft ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `graft grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `graft skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `graft callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `graft/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `graft ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `graft build` (deterministic,
no API key, $0).

## Gotchas

- **Never run `npm run legacy-package` locally.** It destructively rewrites
  `package.json`; CI only runs it inside a throwaway legacy job.
- Do not commit build output or the generated files listed under "Repository
  layout" — they are gitignored and regenerated by the build.
- `graft/` is **not tracked in git** in this repo; run `graft build` to
  regenerate the local graph after large refactors.
- `src/global-config.ts` is marked internal and `src/version.ts` is generated —
  do not add new public surface to either.
- `.mcp.json`, [opencode.json](./opencode.json) and `.claude/settings.json`
  register the graft MCP server; `.claude/skills/graft/SKILL.md` documents it for
  Claude Code. `.github/copilot-instructions.md` mirrors the graft block.
- Adding a new entry point or output directory requires touching several places
  together: `package.json` (`exports`), the `tsconfig*` set,
  [.fatherrc.ts](./.fatherrc.ts), [scripts/copy-lib.ts](./scripts/copy-lib.ts),
  and the Jest/Vitest configs.
